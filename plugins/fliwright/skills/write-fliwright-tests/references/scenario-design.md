# 从测试目标推导用例、场景与 Mock

创建测试或调整覆盖行为时使用本流程。输入可以是自然语言目标、缺陷复现步骤、验收条件或已有用例；不要求 GitLab Item、`plan.json` 或 `test-plan` 命令。仅修改定位器等局部问题时，核对原有目标与前置状态即可，不必重新设计整套用例。

## 推导可验证用例

先区分用户要求的正确行为与当前实现。需求和验收条件决定预期；源码、已有测试及运行事实用于确认到达分支的方法和技术契约。当前缺陷行为不能反向成为正确结果。

把目标拆成可独立验证的行为，按目标涉及的条件考虑成功、空数据、边界、错误、权限和恢复分支。只覆盖有依据且与目标相关的分支，不固定数量或穷举无关组合。不确定的业务规则要列为缺口。

为每条用例明确以下对应关系，可使用简短表格或测试内注释；小任务不需要另建计划文件：

| 内容 | 要确认的事实 |
| --- | --- |
| 目标与预期 | 要验证哪个业务分支，什么可见结果能区分正确和错误 |
| 前置状态 | 认证、业务数据、相关 storage/cache/provider、入口路由及依赖能力 |
| 场景 | 复用、组合或新增的命名场景，为什么能建立所需前置状态 |
| Mock | 关键 method/endpoint、所选规则及触发分支的数据条件；不需要 Mock 时注明原因 |
| 操作与断言 | 用户动作、关键请求事实、结果及必要的恢复检查 |

## 从前置条件构建场景

检查项目配置、`.fliwright/support/`、已有场景及共享 Mock。核对真实 layers、响应内容和 ready 条件，不能仅凭名字相似复用。相同前置条件的多个用例可以共用场景，不要求一条用例对应一个新场景。

- 将可复用基线与业务分支差异拆开，使用命名组合 `TestScenario`，显式注册到现有配置并通过 `test.scenario(name)` 选择。具体声明、单例层限制及重试准备见 [scenarios.md](./scenarios.md)。
- 已登录业务测试用 app-owned `auth.seedLoggedIn`，访客使用清理后的会话。普通业务状态通过真实接口 Mock 或适当的 state/app layer 建立；不要用 provider override 替代认证。
- 初始状态必须能重复建立。检查旧缓存或已加载 provider 是否会阻止目标请求发生，按项目能力清理或重建相关状态，再通过真实业务动作触发加载。需要首帧隔离时使用项目支持的 bootstrap 和 managed launch，不能假设 attach 能重放启动请求。
- 场景只准备动作之前的状态。测试导航就从导航前的入口开始；测试刷新、提交或恢复就保留对应动作，不能预先注入最终成功状态或直接跳到结果页。
- 需要中途改变响应的测试，声明初始场景，在步骤中严格替换响应，再触发真实重试/刷新。`applyRuleSet` 替换完整规则集并清理调用记录；替换前保存仍需验证的请求事实，详见 [mock-rule-sets.md](./mock-rule-sets.md)。

## 从业务分支构建正确 Mock

先确认本次测试的边界：客户端在受控响应下的行为可以使用 Mock；目标是实际后端联调时，保留关键真实调用，不能用 Mock 成功替代联调结果。纯本地行为不必新增网络 Mock。

沿目标 UI 的 controller/provider、repository/API client、响应 model/parser 检查数据来源，必要时使用项目 API 文档或已确认的响应样本。确认：

- 实际 HTTP method、路径，以及决定分支的 query/body 字段。
- HTTP 状态、业务 code、响应信封、字段类型、枚举、缺失/null 和分页结构。HTTP 200 可能仍是业务错误；`success` 规则也可能返回不满足目标的空数据。
- 数据如何到达 UI 分支，相关端点之间的 ID、权限和状态是否一致，以及初始化/刷新还会调用哪些依赖接口。

优先选择语义匹配的已有具名响应；缺少时加载 [write-fliwright-mock-rules](../../write-fliwright-mock-rules/SKILL.md) 创建或补充端点 JSON。普通项目用共享 `.fliwright/mocks/api/`；已有 Item 工作流时才使用 Item 专属目录。沿用真实解析契约，保留所需字段，只修改目标分支需要的差异；不要因为解析失败而编造字段或修改业务代码迎合测试。

使用命名场景的 `sources` + `rules` 显式选择所需响应，组合方式见 [mock-rule-sets.md](./mock-rule-sets.md)，同样适用于无 Item 的项目场景。覆盖继承的 method/endpoint 要写 `replace: true`。检查 `baseRule` 浅合并后的最终 body；字段缺失、null、空字符串和空数组不能互相替代。

覆盖页面所需的相关依赖请求，保持严格的未匹配请求策略。不要为让测试通过而开放真实网络或使用宽泛成功响应掩盖漏配端点。规则无法区分目标所需的请求参数或响应顺序时，核查当前匹配能力，使用明确的步骤切换或报告能力缺口，不假设 schema 支持未定义的匹配字段。

## 验证与交付

1. **离线检查**：核对测试到场景的选择与配置注册，运行适用的 TypeScript 检查。使用 `scenario resolve` 检查场景组合；它不读取端点 JSON，sources 模式还须把完整继承展开后的 sources/rules 交给 `resolveMockRuleSet` 校验。检查解析后的响应是否确实满足目标数据条件，不能仅检查 JSON/schema 合法。
2. **运行检查**：按项目配置运行目标测试。场景准备应严格应用到 Flutter；中途改单条响应使用 `routeFlutter` 等严格接口。用 `findCalls`/`getCalls` 核对目标相关的 method/path、决定行为的参数及必要的次数；不对无关后台请求作脆弱断言。需要验证“不发请求”时，在已确认的操作完成状态之后检查对应调用窗口，不能靠固定 sleep 或动作前的空记录通过。
3. **结果检查**：断言能区分目标分支的可见数据、控件状态、错误提示或导航结果；恢复目标还需验证恢复后的结果。只检查页面存在、路由注册成功或请求数量非零不足以证明业务分支。Mock 控制的数据分支应有对应请求事实及 UI 结果；无请求目标则验证预期的本地行为。
4. **交付说明**：简述目标到用例、场景和关键规则的对应关系，列出文件及检查结果。有真实运行时引用其 run/attempt 和相关产物；适用时从 timeline `mockRuleSet` 核对实际激活来源。规则指纹只能证明激活配置，不能证明请求使用或业务通过。没有设备、VM Service、契约或能力时继续可做的工作，并明确未验证内容和具体缺口。

测试注册或参数化发生变化时，另按 [Vitest 收集检查](./vitest-authoring.md#用例收集与交付)核对名称、数量和编辑器发现；精确次数与无请求的观察窗口见 [请求断言](./assertions.md#请求断言)。

用户要求实现测试时，场景推导、所需规则编写、配置接入和适用验证由当前会话连续完成，不要求用户逐个指定场景或规则。只要求用例设计时，交付所需前置条件和数据设计，不扩展到修改配置或运行 App。真实业务缺陷保留失败证据，修复范围依用户任务而定，不弱化断言。
